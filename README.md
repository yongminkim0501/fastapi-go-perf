# msa-perf-lab

> MSA 환경에서 **병목의 유형을 식별하고, 아키텍처 선택의 손익분기점을 정량화**하는 성능 실험 프로젝트

FastAPI 게이트웨이와 Go 코어 서비스를 대상으로, 부하를 계단식으로 올려가며 각 구성의 포화점(knee)을 찾고 그 원인을 런타임 내부까지 추적한다.

---

## 핵심 질문

이 실험이 답하려는 것은 "Go가 Python보다 빠른가"가 아니다.

1. **언제** 무거운 연산을 Go로 위임할 가치가 있는가 — 통신 비용을 상쇄하는 연산 시간의 손익분기점은 몇 ms인가
2. Python의 성능 저하 중 **GIL이 차지하는 몫**은 얼마이며, 어떤 워크로드에서 사라지는가
3. `async def`는 언제 이득이고 언제 재앙인가 — CPU-bound와 I/O-bound에서 결론이 뒤집히는 지점

---

## 시스템 구조

```
k6 ──▶ FastAPI 게이트웨이 :5001 ──┬──▶ 내부 연산 (Python)
                                  ├──▶ Go gRPC 위임 :50051
                                  └──▶ Go 직접 호출 :8080  (베이스라인)
```

| 구성요소 | 역할 |
|---|---|
| FastAPI 게이트웨이 | 트래픽 진입점, 실험 대상 |
| gocore (Go) | REST :8080 + gRPC :50051 |
| PostgreSQL | I/O 대기 워크로드 (`pg_sleep`), 커넥션 풀 실험 |
| Redis | 캐시 히트율 실험 |
| RabbitMQ | 비동기 처리, 큐 적체 실험 |
| Prometheus + cAdvisor + node-exporter | 시스템 자원 수집 |
| InfluxDB + Grafana | k6 결과 저장 및 시각화 |

## 실험 설계

### 조건 축

| 축 | 수준 |
|---|---|
| 워크로드 | 정수 루프 / SHA-256 / JSON 직렬화 / NumPy 행렬 |
| 연산 난이도 | `complexity_level` 계단식 증가 |
| 부하 강도 | RPS 램프업으로 포화점 탐색 |
| CPU 할당 | 0.5 / 1 / 2 / 4 코어 |
| 워커 수 | 1 / N / 2N |
| 동시성 모델 | `def` / `async def` / ProcessPoolExecutor |
| 인터프리터 | CPython 3.14 / free-threaded 3.14t |
| 처리 경로 | Python 내부 / Go gRPC 위임 / Go 직접 호출 |

### 통제 원칙

축을 전부 곱하면 4,000가지가 넘는다. **한 번에 하나의 축만 움직이고 나머지는 기준 구성에 고정한다.**

기준 구성: `정수 루프 / 2코어 / 워커 1 / def / CPython / Python 내부`

이 방식으로 축당 3~5회, 전체 20~30회 실행으로 1차 스캔이 끝난다.

## 측정 지표

### 상시 수집 — 자동으로 쌓이며, 이 중 4개만 매 실행 판독

**판독용 (실험 중 계속 확인)**

| 지표 | 설명 | 판단 기준 |
|---|---|---|
| `http_reqs` | 실제 소화한 처리량 (RPS) | 목표 RPS에 못 미치면 포화 |
| `dropped_iterations` | k6가 쏘지 못하고 버린 요청 | **포화의 실제 신호.** 이게 늘면 p95는 오히려 좋아 보인다 |
| `http_req_duration` p95 | 응답 시간 상위 5% | 무릎 판정의 주 지표 |
| 컨테이너 CPU 사용률 | gateway vs gocore | 포화 원인 갈래를 나눔 |

**기록만 (사후 분석용)**

- `http_req_waiting` — TTFB. 네트워크 대기와 서버 연산 분리
- `http_req_failed` — 실패율. 대개 다른 병목의 *결과*이므로 상태 코드와 함께 봐야 함
- `vus` — 활성 VU 수. 리틀의 법칙(평균 고객 수 = 평균 도착률 × 평균 체류 시간)으로 교차 검증
- `server_time_ms` — 응답 body의 서버 자체 측정값. 게이트웨이 오버헤드 분리
- 코어별 CPU 사용률 — Python이 단일 코어만 쓰는지 육안 확인
- 메모리 / RSS 추이
- CPU throttling (`container_cpu_cfs_throttled_periods_total`) — `cpus` 제한 시 필수
- 컨텍스트 스위치, run queue 길이
- 네트워크 I/O — gRPC 위임 경로의 통신 비용

### 진단용 — 이상 신호가 잡힌 지점에서만 실행

프로파일러는 대상 프로세스를 느리게 만들어 측정값 자체를 오염시킨다. 상시 수집하지 않는다.

**Go**
- goroutine 수 추이
- GC pause 분포, GC 사이클 빈도 (`GODEBUG=gctrace=1`)
- CPU 프로파일 / 플레임그래프 (`net/http/pprof`)
- heap 할당률

**Python**
- 플레임그래프 — 시간이 어디서 소모되는가 (`py-spy record`)
- GIL 점유 상태 (`py-spy dump`)
- 워커 프로세스별 CPU 분배
- 이벤트 루프 블로킹 시간 (`async def`인 경우)

**저수준 (perf)**
- IPC (instructions per cycle) — 진짜 CPU-bound인지 증명
- cache-miss율
- 초당 컨텍스트 스위치 수

## 판독 절차

### 1단계 — 매 실행 후 3개만 본다

RPS가 목표만큼 나왔는가 / `dropped_iterations`가 0인가 / p95가 무너졌는가.
셋 중 하나라도 무너지면 그 RPS가 이 구성의 포화점이다. 여기서 판정을 끝내고 다음 조건으로 넘어간다.

### 2단계 — 무릎 지점에서 CPU 사용률 한 번 확인

| 결과 | 해석 | 다음 행동 |
|---|---|---|
| 할당량 대비 100% 근접 | 정상 포화. 예상된 한계 | 기록하고 종료 |
| CPU가 남는데 포화 | **이상 신호** | 3단계로 |

### 3단계 — 증상별 진단

| 증상 | 의심 | 확인할 것 |
|---|---|---|
| 코어 여러 개인데 1개만 100% (Python) | GIL | `py-spy dump`로 스레드 상태 |
| CPU 남는데 latency 높음, `async def` 사용 | 이벤트 루프 블로킹 | py-spy 플레임그래프 |
| Go인데 p99만 튐 | GC pause | `gctrace`, heap 할당률 |
| CPU 남는데 컨텍스트 스위치 폭증 | 스케줄링 병목 | run queue 길이, perf `cs` |
| CPU 그래프는 여유 있는데 처리량 정체 | cgroup throttling | `container_cpu_cfs_throttled_periods_total` |
| 위임 경로만 느림, 양쪽 CPU 모두 여유 | 통신·직렬화 비용 | 네트워크 I/O, gRPC 채널 재사용 여부 |
| CPU 100%인데 IPC 낮음 | 메모리 대기 | perf `stat` — IPC, cache-miss |

## 실험 시나리오 예시

### 0. 캘리브레이션 — `complexity_level`을 ms로 환산

RPS=1(동시성 없음)로 각 난이도를 30초씩 실행해 `server_time_ms`를 수집한다.
이 표가 있어야 Python과 Go를 **같은 연산 시간**에 놓고 비교할 수 있다.

| complexity | Python (ms) | Go (ms) |
|---|---|---|
| 1 | — | — |
| 5 | — | — |
| 25 | — | — |
| 100 | — | — |
| 500 | — | — |

여기서 이미 결과가 하나 나온다 — 같은 시간을 만드는 데 필요한 난이도의 비율이 곧 두 런타임의 순수 연산 성능비다.

### 1. 층별 분해 — 각 계층의 비용을 뺄셈으로 얻는다

| 층 | 측정 대상 | 뺄셈 결과 |
|---|---|---|
| L0 | 함수 직접 호출 (`timeit`, `go test -bench`) | 런타임 자체 연산 성능 |
| L1 | HTTP 핸들러 경유 (RPS=1) | L1 − L0 = **프레임워크 오버헤드** |
| L2 | 게이트웨이 → Go gRPC 위임 | L2 − L1 = **통신·직렬화 비용** |
| L3 | 동시 부하 상태 | L3 − L2 = **큐잉·경합 비용** |

L0은 HTTP를 태우지 않는다. k6 없이 컨테이너 안에서 함수만 직접 측정한다.

### 2. RPS 범위를 이론에서 유도

감으로 찍지 않는다.

```
이론상 최대 처리량 = 동시 처리 가능 수 ÷ 연산 시간
이용률 ρ = 실제 RPS ÷ 최대 RPS
```

**예시**: 50ms 연산, 워커 1개, 1코어 → 최대 20 RPS

ρ 기준으로 스윕: **6 / 10 / 14 / 16 / 18 / 20 / 24 RPS** (ρ = 0.3 ~ 1.2)

ρ가 0.7을 넘으면 큐잉 지연이 붙기 시작하고, 1에 근접하면 latency가 수직으로 튄다.
실측 무릎이 이론값(20)과 어긋나는 폭이 곧 **인터프리터·GIL·컨텍스트 스위칭이 먹은 오버헤드**다.

### 3. 노브를 돌렸을 때 무엇이 움직이는가

저부하 구간에서는 구성을 바꿔도 latency가 거의 변하지 않는다. 대기가 없기 때문이다.
따라서 고정 RPS 한 점만 재면 "차이 없음"이라는 잘못된 결론이 나온다.
**곡선 전체를 뽑아 무릎의 위치를 비교한다.**

| 노브 | 예상되는 변화 |
|---|---|
| 워커 수 ↑ | 무릎만 오른쪽으로. 저부하 latency 불변 |
| CPU 코어 ↑ | 무릎만 오른쪽으로. **Python 단일 워커면 안 움직임 ← GIL의 증거** |
| Go 위임 | 저부하 latency는 **상승**(통신 비용), 무릎은 크게 오른쪽으로 |
| 워크로드 → SHA-256 | Python 무릎이 급개선 (C 확장이 GIL 해제) |

### 4. 병목 유형 확장 — CPU 외의 실험

동일한 판독 절차를 병목 종류만 바꿔 재사용한다.

| 병목 | 만드는 법 | 특징적 증상 | Go 위임이 도움? |
|---|---|---|---|
| CPU | 연산 루프 | CPU 100%, 코어 늘리면 개선 | 예 |
| I/O 대기 | `pg_sleep(0.05)` | CPU 한가한데 latency 높음 | 아니오 (async가 답) |
| 커넥션 풀 경합 | 풀 크기 5로 제한 | latency가 **계단식**으로 점프 | 아니오 |
| 큐 적체 | 컨슈머보다 빠르게 유입 | 큐 깊이 증가, end-to-end 지연 | 경우에 따라 |
| 메모리 / GC | 대량 객체 할당 | p99만 주기적으로 튐, RSS 우상향 | 경우에 따라 |

CPU-bound와 I/O-bound를 나란히 놓으면 `async def`에 대한 결론이 정반대로 나온다.
이 대비가 이 프로젝트의 핵심 산출물이다.

## 측정 신뢰성

- 조건당 최소 5회 반복, **중앙값과 신뢰구간**을 함께 보고
- 워밍업 10초 구간 제외
- 측정 중 Grafana·InfluxDB는 별도 호스트에서 실행하거나, 측정 후 일괄 수집

- Go 연산 함수 내부의 로깅 제거 (초당 수천 줄의 stdout I/O가 측정 노이즈로 유입)

## 알려진 한계

단일 호스트 마이크로벤치마크이므로 다음은 재현되지 않는다. 결과 해석 시 반드시 감안한다.

- **네트워크 지연** — 모든 컨테이너가 동일 호스트에 있어 RTT가 0에 가깝다. 실제 MSA에서 gRPC 위임 비용은 여기서 측정한 값보다 크다
- **수평 확장** — 인스턴스 1대 기준이라 로드밸런싱 효과를 관측할 수 없다
- **콜드 스타트 / 캐시 워밍** — 워밍업 구간 제외와 함께 사라진다
- **혼합 워크로드** — 실제 트래픽은 무거운 요청과 가벼운 요청이 섞이며, 그때 큐잉 동역학이 달라진다
